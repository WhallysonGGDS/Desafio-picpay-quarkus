Não rodei `npm audit fix --force` (exigiria vitest 5 ou openapi-typescript 6, fora da cadeia verificada) — custo se errado: exposição só na máquina de quem roda os testes; reavaliar ao atualizar o Vitest.
- Task 1: Ruling R6: o Quinoa 2.5.5 NÃO consegue fazer o fallback do SPA atrás do `GlobalExceptionHandler` do Plano A. Causa (medida no bytecode do RestInitialHandler 3.15.1 e no jar rodando: `/carteira` → 404 JSON do meu mapper, sem nenhum "re-routing" no log do Quinoa): quando nenhum recurso casa com o caminho, o REST só repassa o pedido adiante se `getExceptionMapper(NotFoundException)` for null; o mapper `ExceptionMapper<Exception>` existe, então o REST responde o 404 sozinho. Decisão: manter o Quinoa para build/estáticos/proxy de dev e servir o fallback com um `SpaFallback` (Vert.x `Filters`, roda antes do REST), só no perfil prod e só quando o Quinoa está ligado, reaproveitando `quarkus.quinoa.ignored-path-prefixes`. É o "plano B" que a spec §5.1 já prevê (rota de fallback própria). Custo se errado: ~40 linhas de Java a mais; se o Quinoa um dia respeitar o mapper, basta apagar a classe.
- Task 1: Ruling R7: o fallback só reescreve GET/HEAD com `Accept: text/html` (navegação), sem ponto no último segmento e fora dos prefixos da API — cliente de API que erra a URL continua recebendo o JSON 404 do contrato; arquivo ausente (`/assets/x.js`) continua 404 em vez de virar HTML. O plano não pedia o `Accept`; o IT envia o Accept de um navegador (`text/html,application/xhtml+xml,*/*;q=0.8`). Custo se errado: curl sem Accept em rota do SPA recebe 404 JSON.

Corrigidos application.properties (`%test.quarkus.quinoa=false`; o Quinoa já é desligado em testes por padrão) e o texto da T15 (README). Custo se errado: nenhum.
